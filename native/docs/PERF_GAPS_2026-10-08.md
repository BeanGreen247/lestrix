# Performance gap analysis (2026-10-08)

Static reading of the I/O path (`native/src/ui/tcore.c`, `native/src/pty.c`, `native/tools/lxcat.c`, `native/src/vt.c`) against the `developer-performance-opt` method. Nothing below is measured unless it says so: each item is a candidate with the experiment that would decide it. Diagram: `terminal-io-diagram.html`.

Measured facts used as the frame (this repo's own numbers): parse path without newlines 2.1 GB/s (floor); serial gate 1429 -> ~1580 MB/s, with scrollback 690 -> ~790 MB/s (README row 36); pty with kernel newline processing 0.09 GB/s, without 0.42-0.46 GB/s; ASCII flood through lxcat 0.18 s for 256 MB (about 1.4 GB/s).

| # | Gap (file) | Why it costs | Experiment that decides it | Risk |
|---|---|---|---|---|
| 1 | DONE 2026-10-08 (shadow rows, README row 37: gate with scrollback 790 -> about 900 MB/s, 170-char lines 1130 -> 1400) - was: Scrollback path still about 2.6x below the 2.1 GB/s floor (`vt.c` `hist_push`, `hist_add_compact`, `pack_oldest`) | Each scrolled row is re-read cell by cell to check "all ASCII, one style" and packed to bytes; the block is later packed again | Track an "ASCII + uniform style" flag per row at write time in `put_ascii` (cleared by every other writer) and skip the pass; upper bound: delete the check and time it | Medium: every cell writer must clear the flag; fuzz with `test_fast_paths` |
| 2 | Non-whitelisted programs pay kernel newline processing (`tcore.c` `fo_comm_ok`: fixed list of 48 names) | Anything not in the list (git log, journalctl, python, node, most scripts) stays at about 0.09 GB/s | Run `ptybench` style output from an unlisted program with OPOST on vs off and `force_nl` on; check programs that print bare `\n` expecting staircase never exist under ONLCR anyway | Medium: needs the owner's call (changes which programs run with a modified tty) |
| 3 | DONE 2026-10-08 (splice, README row 38: about -4 to -9% end to end; mmap rejected, SIGBUS risk) - was: lxcat does 3 copies of every byte: pipe -> lxcat buffer -> tmpfs file -> terminal pread buffer (`lxcat.c` `stream_stdin`, `tcore.c` `stream_file`) | 8 MB and 1 MB copies at about 14 GB/s single-thread read bandwidth | `splice()` pipe -> tmpfs file (kernel to kernel), and `mmap` the file in the terminal instead of `pread` into a 1 MB buffer; time 256 MB through a pipe | Low-medium: splice into tmpfs is supported; keep the current path as fallback |
| 4 | REJECTED 2026-10-08 (inotify: no gain, 0.617/0.563 vs 0.529/0.570 s; the terminal side is the limit, see PERFORMANCE doc) - was: lxcat waits for the terminal with `access()` + `nanosleep(500 us)` polling (`lxcat.c`, two spots) | Up to 0.5 ms idle per hand-off and a wake-up per poll; with 8 MB chunks it is small, with small pipes it is not | Replace with an eventfd/pipe acknowledgement or `inotify` on the unlink; measure hand-off gaps with `strace -T` | Low |
| 5 | REJECTED 2026-10-08 (spin 2000/200/0 all within noise, 0.32-0.38 s) - was: `feed_sliced` spins with `sched_yield()` up to 2000 times while the UI waits for the lock (`tcore.c`) | Burns CPU on the parse thread exactly when a core is wanted for rendering | Count yields per second under a flood with the UI visible; try a futex/condvar handoff or a shorter spin | Low |
| 6 | DONE 2026-10-08 (head offset, README row 39: 8 MB queue 0.42 -> 0.07 s in a micro-benchmark) - was: `flush_out` does `memmove` of the whole remaining queue after every partial write (`tcore.c`) | O(n^2) for a large paste into a slow reader; invisible for keystrokes | Paste 50 MB into `cat > /dev/null` under a profile; replace with a head offset | Low |
| 7 | Reader sleeps 200 us after any read under 1 KB (`reader_main`) | Documented trade for fewer wakeups; adds up to 0.2 ms to the second echo chunk | Typing echo latency, xdotool key-to-pixel, before/after; hard rule: no typing lag | Keep unless measured harmless |
| 8 | Parser holds `t->lock` for each 64 KB slice; the UI thread competes (`feed_sliced`) | Contention shows up as `ui_waiting` spins (item 5) | Lock hold time per slice vs frame time at 60 fps; smaller slices only if the UI stalls | Low |
| 9 | Bulk parallel parse starts at 128 KB (`BULK_MIN`) while reads from the pty arrive in 4-64 KB pieces | The fast serial path (this session's rows) is what real pty traffic uses, so serial speed matters more than bulk | Histogram of read sizes in a real `ls -R` / `make` flood (`reads` counter in the perf bar) | Information only |
| 10 | Render side not analysed here (`render.c`, `termview.c`, `atlas.c`) | Dirty-row logic exists; GPU vs CPU split not re-measured since 2026-10-05 | `native/benchmark` render phase per frame; fleetwm `case-desktop-compositor-field-notes` method | Open |
